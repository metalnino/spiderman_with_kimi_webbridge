# 源头追溯（源头追溯员 / tracer）—— 设计、边界与实测

> 2026-09-20 立项。起因：采集员把公告采回来后，台账里下一步就断了 ——
> 「这条上海职场绿植租摆服务采购询比采购公告，源头其实是华能集团电子商务平台的一手公告，
> 而且那里还能直接下载采购文件」这件事，采集员不该管，也确实没管。
> 本文回答三件事：**为什么必须是独立岗位**、**怎么做**、**实测做到了什么程度**。

---

## 0. 结论先说

1. **这是新岗位，不是采集员的活。** 粒度、成本模型、失败语义三样全不同（见 §2）。
2. **追溯的关键不是爬虫，是「锚点 + 平台知识」。** 一手平台几乎都有 WAF/JS 渲染（华能纯 HTTP 412、
   东部机场 502），但真正难的不是抓，是**知道去哪儿抓**。所以内核是「锚点抽取 + 平台登记表」，
   爬虫只是最后一公里。
3. **重复工作量的问题有确定性答案**：追溯按 `project_key` 作业，同一项目在 4~9 个聚合站的重复条目
   **只追一次**，结果广播给整组；追溯结果写 `origin_*` 独立列，不覆盖采集员的 `detail_status`。
4. **AI 的位置是「抽锚点」，不是「下结论」。** 源头认定必须由页面证据（项目核心名/项目编号/日期）
   支撑；AI 抽错锚点最坏结果是多试几个候选，不会写出假源头。
5. **实测**：华能案例端到端跑通（一手正文 1761 字，置信度 0.98）；招必得案例拿到签章版
   采购文件 PDF（184KB，含最高限价 19.6406 万元）。找不到的案例**如实输出 not_found + 候选清单**，
   不编造。

## 1. 第一性原理：什么叫「源头」

把链条拆到最基本事实：

```
招标人（华能天成融资租赁）
   └─ 在自己的电子采购平台发布 ← 【源头：一手正文 + 可下载采购文件】
        └─ 被 yfbzb 转载（可能是加密/登录墙）
        └─ 被 chinabidding 转载（登录墙，正文只剩「立即注册查看」）
        └─ 被 qianlima 转载（正文可达但字段遮罩）
        └─ 被 bidcenter / okcis / caizhaowang … 再转载（我们根本不采这些）
```

由此得到四个可判定的事实：

| 事实 | 推论 |
| --- | --- |
| 聚合站正文常常是残缺的（登录墙/乱码/字段遮罩） | 只靠聚合站，下游解析员拿不到可解析的招标文件 |
| 一手平台有完整正文 + 采购文件下载 | 一手正文是**唯一能支撑投标决策的依据** |
| 同一项目在多个聚合站重复出现 | 追溯必须以「项目」为单位，不能以「公告条目」为单位 |
| 一手平台的发布位置是可枚举的（招标人自建 / 政府平台 / 第三方交易平台） | 平台知识可以**积累**，越用越准 |

### 采集员的数据现状（这就是缺口）

绿植族（`绿植租摆|绿植租赁|植物租摆|植物租赁`）438 条：

| 指标 | 数量 |
| --- | --- |
| 总条目 | 438 |
| `detail_status='ok'` | ~12 |
| 有可下载附件 | 1 |
| 有原发线索 `original_url` | 3 |

即：**采集广度已经够了，深度是 0**。而这 438 条背后其实只有 ~180 个项目（平均 2.4 个站重复），
追溯的工作量比看上去小得多。

## 2. 为什么是独立岗位（与采集员的边界）

| 维度 | 招标采集员 | 源头追溯员 |
| --- | --- | --- |
| 作业单位 | 站 × 关键词（出勤） | **project_key**（一个项目一次） |
| 目标 | 广度/时效：不漏 | 深度/质量：一手正文 + 采购文件 |
| 预算 | 每轮 42 词 × N 站，必须压住 | 单条可开真浏览器、跑检索、下附件（秒~分钟级） |
| 失败语义 | **绝不阻塞出勤**，失败降级继续 | **允许终态为 blocked / not_found**，并要求人工接手 |
| 产物 | notices 列表行 + 详情字段 | 一手正文 + 附件 + 源头台账（origin_*） |
| 依赖 | HTTP/桥、反爬策略 | + 平台登记表、外部检索、AI 锚点 |

塞回采集员的三个直接后果：① 同一条公告在 4 个站被追溯 4 次（用户担心的重复工作量就是这个）；
② 单条分钟级深挖会拖垮出勤预算；③ 「找不到源头」这种**需要人工的失败**混进采集员的
`detail_status`，把「没采到」和「追不到」两种语义搅在一起。

### 去重口径（回答「会不会和采集员重复」）

1. **按项目去重**：`project_key = sha1(city|核心项目名)`（既有字段）。同组只追一次，结果广播全组
   （实测 7 条公告共享 1 次追溯）。
2. **按列隔离**：追溯写 `origin_level / origin_portal / origin_detail_url / origin_status /
   origin_confidence / origin_evidence / origin_traced_at`；采集员的 `detail_status` 不动。
3. **按证据覆写正文**：`summary` 只在源头正文**严格更好**时覆写（旧值为空/乱码，或新正文 ≥ 旧 1.2 倍）；
   一旦拿到原始采购文件附件则无条件覆写（附件是一手依据）。`tenderfile_path` 只在原为空时写入。

## 3. 三层内核

```
① 锚点层  crawl/origin_hints.py     规则 + AI 从正文/标题抽「找源头的钥匙」
② 平台层  crawl/origin_portals.py   config/origin_portals.json 声明式适配器 + 桥驱动 + 外部检索
③ 编排层  crawl/origin_trace.py     选种子 → 汇聚锚点 → 找源头 → 校验 → 取回 → 落库
```

### ① 锚点层：找源头的钥匙是正文里的身份信息

规则抽「确定的东西」（确定性 > 概率性）：

| 锚点 | 例子（华能实测） | 为什么是钥匙 |
| --- | --- | --- |
| 采购人/招标人 | 华能天成融资租赁有限公司 | 直接映射到主体自己的采购平台 |
| 邮箱域名 | `baonike@huanengleasing.com` → huanengleasing.com | 企业域名，能反查主体官网 |
| 正文 URL | `https://ec.chng.com.cn/` | 常常直接就是发布平台 |
| 项目/采购编号 | `HNFZ2026-09-2-00396` | 唯一键；但注意多数平台**按标题检索**，编号搜不到 |
| 发布媒介行 | 「本公告在中国华能集团电子商务平台发布」 | 最直白的源头证据 |

AI（DeepSeek，复用 `config/ocr_api.json`）只补规则抽不到的**语义字段**：主体规范全称、主体简称、
正文里提到的平台名。抽不到一律 null；失败/无 key 自动降级纯规则（不改采集主链）。

**兄弟公告补锚点**（实测踩出来的必需项）：同一项目的「招标公告 / 变更公告」`project_core` 不同，
会落进不同 `project_key`；实测 50343「上海职场绿植租摆服务采购询比采购公告」标题里**根本没有主体名**，
而同项目的变更公告标题里有。所以锚点要从同城近同标题的兄弟公告汇聚（Dice ≥ 0.5，LIKE 核心片段约束）。

### ② 平台层：声明式适配器（新增源头只加数据）

平台差异被压成三类声明，代码只做「打开 → 取行 → 取 id → 打开详情」这一套通用动作：

| adapter | 适用 | 声明内容 |
| --- | --- | --- |
| `bridge_spa_search` | SPA + 表格检索（华能） | 检索 URL 模板、行选择器、行 key 属性、详情 URL 模板 |
| `bridge_page` | 有详情页即可（招必得） | 外部检索定位详情页后直接桥渲染 |
| `http_detail` | 已有 HTTP 解析器（ccgp/jsggzy） | 复用既有能力，不重写 |

实测华能适配器只需 6 行 JSON：

```json
"search": { "url": "https://ec.chng.com.cn/channel/home/#/search?value={kw}",
            "rowSelector": "tr.ant-table-row", "rowKeyAttr": "data-row-key",
            "rowTitleSelector": ".table-item" },
"detail": { "url": "https://ec.chng.com.cn/channel/home/#/detail?id={id}" }
```

**桥是必需品不是优化项**：华能纯 HTTP 一律 412（WAF），东部机场 502；只有真浏览器能过。

外部检索（Bing，桥内）+ 四类检索词（项目编号 / 核心名 / 主体+「招标采购交易平台」/ 核心名+原始公告），
多条查询结果**取并集**（单条 query 首页常整页是镜像站，早停会漏掉真源头）。

### ③ 校验：四道关（防假阳性，这是本项目最容易翻车的地方）

实测把「校验」做严之前，程序会把**企查查的公司主页**当成源头，会把**去年的同名公告**当成今年的源头。
现在的四道否决：

| 否决 | 触发 | 实测拦下的 |
| --- | --- | --- |
| `non_source_domain` | 企查查/天眼查/百度百科等企业信息站 | `qcc.com`（曾被误认成源头） |
| `mirror_page` | 镜像品牌名（中国采购与招标网等）/ 会员门 ≥2 处 | 多个聚合站 |
| `list_page` | 「公告/公示」出现 ≥20 次（或 ≥12 次且正文 <2000 字） | `m.bidnews.cn` 公司专栏页（22 次） |
| `no_project_anchor` | 正文里对不上**项目核心名或项目编号**（只对得上采购人名不算数） | 各种同名干扰页 |
| `date_mismatch` | 页面日期与该次采购相差 >45 天 | ccgp 上同一学校的 2026-07 另一标（DB 是 2026-09） |

判定用 **Dice 相似度**（`2|A∩B|/(|A|+|B|)`）而不是覆盖率：覆盖率会把「上海职场绿植租摆服务」(10 字)
和「华能天成融资租赁有限公司上海职场绿植租摆服务项目」(24 字) 都判成 1.0，抓错详情 id（实测踩过）。

## 4. 落库与交接

```
MySQL notices.origin_*          ← 追溯台账（与采集状态分离）
reports/origin-trace-report.json ← 本轮报告（含每条 traces）
handoffs/tracer/latest.json      ← 管道交接物（下游/人可直接读，tracer/v1.0.0）
```

契约：`AI员工岗位体系/contracts/tracer/v1.0.0.json`；注册表已登记 `tracer`（status=current）。

CLI：

```bash
python scripts/migrate_origin_trace.py                                  # 建列（幂等）
python scripts/origin_trace_run.py --list                               # 看待追溯项目组
python scripts/origin_trace_run.py --notice 50343 --apply               # 追单条并落库
python scripts/origin_trace_run.py --limit 3 --apply                    # 批量（绿植族默认词）
python scripts/origin_trace_run.py --project-key <sha1> \
       --origin-url "https://..." --apply                               # 人在环：人工给源头链接
```

## 6. 回答最初的三个疑问

**Q1「这部分是不是采集员的事？」**
不是。追溯的单位是项目、预算是分钟级、失败允许终态并要求人工接手 —— 三条都和采集员相反。

**Q2「会不会和采集员重复、工作量变大？」**
不会，前提是三条口径落地：① 按 `project_key` 追一次、广播全组（7 条公告 = 1 次追溯）；
② 追溯只在聚合站正文**不可用**或**源头有更完整内容/附件**时才覆写正文；
③ 追溯结果与采集状态分列，互不覆盖。真正省下来的工作量是：下游解析员第一次能拿到一手正文。

**Q3「AI 接入到什么程度？」**
AI 负责**语义锚点抽取**（主体全称/简称/正文提到的平台名）和**候选排序建议**；
**认定源头必须靠页面证据**（核心名/编号/日期三样硬锚点）。
这样即使 AI 抽错，最坏也只是多试几个候选，不会写出假源头 —— 这条红线写进了契约。

**Q4「保存什么？」**
① 一手正文 → `notices.summary`（更好时才覆写）+ 附件 → `notices.tenderfile_path`；
② 招标网址 → `notices.origin_detail_url`（源头详情页）+ `original_url`（与采集员 P5 同语义）
+ `origin_portals.json` 的平台首页/检索模板（**后续直接搜索用**，就是用户说的「保存对应的招标网址，
以便后续直接搜索」）；
③ 追溯证据 → `origin_evidence`（方法/锚点/候选/否决原因，可审计）。

## 7. 深度复盘：为什么"找不到"（2026-09-20 第二轮，用户追问后）

用户的问题：**「是不是理论上都能找到源头？还是你的方法不对导致没找到？」**
答案：**当前所有失败都是方法问题，没有一例是"源头不可达"。** 下面是用实测数据做的证明。

### 7.1 先量分母：源头其实是个「有限枚举集」

| 事实 | 数字 |
| --- | --- |
| 绿植族条目 / 项目 | 507 条 / **239 个项目**（平均 2.1 站重复） |
| 其中已含 gov·法定平台行的项目 | 28 |
| 纯聚合站、源头不在库内的项目 | **211** |
| 纯聚合站项目里"聚合站正文可用"（≥400 字）的 | **5 / 211** |
| 完全没有正文的 | 204 |

两条结论：① 聚合站的正文基本是废的（登录墙/乱码/字段遮罩），**追源头不是锦上添花而是唯一出路**；
② 源头按"谁先发布"只分四类，都是有限集：**法定平台**（ccgp/ggzy/省级，我们已在采）、
**央企国企自建电商平台**（华能/招商局/华润/中煤…，几十个量级）、
**企业官网自建采购栏目**（温州银行 `wzbank.cn/purchase_info`、安徽交控 `ahjg.com` 询比采购栏目）、
**地方交易平台**（招必得、各地公共资源交易中心）。**有限集 ⇒ 理论上都能找到，且平台知识可积累。**

### 7.2 再定位病因：4 个"找不到"的案例，真源头全都进了候选

用检索工具人工复核，4 个失败案例的真源头分别是：

| 案例 | 真源头 | 我们是否碰到过它 |
| --- | --- | --- |
| 温州银行杭州大楼绿植租摆 | `wzbank.cn/purchase_info/view/page_id/36919`（官网，正文+4 个 docx 附件全公开） | ✅ **候选第 1 位**，被自己的判据筛掉 |
| 安徽交控花卉绿植租赁 | `ahjg.com/display.php?id=12479`（官网「询比采购」栏目） | ✅ 候选第 1 位 |
| 南京师范大学相城实验小学 | `czju.suzhou.gov.cn`（相城区政府采购） | ✅ 候选第 3 位 |
| 深圳国际交流中心会议酒店 | `szexgrp.com`（深圳交易集团，**我们自己的源站**） | ✅ **库里就有这一行** |

**没有一例是"源头不存在/不可达"。** 全部是我的判据与流程的问题。

### 7.3 逐条病因 → 修复（每条都对应一个真实失败，且都有回归用例）

| # | 病因（实测） | 修复 |
| --- | --- | --- |
| 1 | **检索词选错**：用「核心名」「核心名+原始公告」「主体+招标采购交易平台」全被镜像站占满；换成 **`{主体} 采购公告`** 后温州银行/安徽交控**第 1 位**就是官网 | `search_queries` 重排：主体+采购公告 > 主体+招标公告 > 主体+核心名；删掉实测零命中的词（含回归用例） |
| 2 | **只看一个 URL**：搜索引擎对企业官网返回的是**站点/栏目首页**（温州银行栏目在 `:8087`、安徽交控在 `info.php?class_id=104101`），只判断"这一个 URL 是不是详情页"必然全判 `no_project_anchor` | 新增**站点级下降** `descend()`：首页链接 → 采购栏目 → 栏目内匹配 → 详情页 |
| 3 | **栏目页只列最新**：目标公告在第 3~4 页 | 新增**有界翻页**：认三种分页形态（「下一页」文本 / `?page=N` / **路径分页 `/list/page/2`**），并用**发布日期早停**（列表按时间倒序，某页最新日期已早于目标就停） |
| 4 | **`project_core` 剥掉阶段词后拿去原文匹配**：标题含「、（三次）」时永远匹配不上（安徽交控） | `hard_hit` 改成「两边都用同一函数只去标点归一化」+ 额外比一次**完整标题** |
| 5 | **`domain_of` 去掉端口**：`wzbank.cn:8087` 的采购栏目被 80 端口主站 URL 挤掉（去重键冲突） | 候选去重键改用 `netloc`（**含端口**） |
| 6 | **链接文本截断到 80 字**：阶段词「询价公告」在末尾被截掉 → 阶段比对失效 | 保留 200 字；阶段判据改成「**不冲突即可**」（链接常只写项目名、没有"公告"二字，严格相等会误杀） |
| 7 | **列表页判据误杀一手详情页**：温州银行官网详情页因侧栏挂了一堆公告链接被判 `list_page:21` | `list_page:` 降为弱信号，用**正文特征**对冲（有"投标人资格/获取招标文件/联系人/电子邮箱"等 ≥2 个信号就是详情页） |
| 8 | **标题相似度当关卡过严**：一手页的 `<title>` 常是「询比采购公告 - XX集团」，Dice 天然低，把已命中的真源头又挡回去 | 页面含**完整标题**即认定（`title_hit`），不再要求 Dice 达标 |
| 9 | **未知域一律不信**：`diuta.com` 这类不在名单里的镜像详情页内容完整、拦不住 | 引入**一手性分级** `trust`：登记平台/gov/含**自域邮箱**（页面里给 `xxx@wzbank.cn` ⇒ 这就是采购人自己发的）→ high；否则 low → 只标 `partial` 交人工 |
| 10 | **自有平台被当成聚合站**：`szexgrp.com` 同时在 `aggregatorDomains`，导致 10 行一手页被定性为聚合站 | 登记表新增 `szexgrp` 平台条目（自有平台 ≠ 聚合站），并从聚合站名单移除 |
| 11 | **库内通道源站名单不全**：只列了 ccgp/ggzy/jsggzy/cebpub，漏了 szexgrp | 补入；库内命中**零网络成本** |
| 12 | **失败不落库**：`not_found` 不写 origin_* ⇒ 下轮重复查、人工看不到待接手清单 | 所有终态都落库（正文仍只在 ok/partial 时覆写） |

### 7.4 修复后战果（同一批样例重跑）

| 案例 | 修复前 | 修复后 |
| --- | --- | --- |
| 上海职场绿植租摆（华能） | ok | ok（保持） |
| 深圳国际交流中心会议酒店 | not_found | **ok** — 库内通道命中 `ygcg.szexgrp.com`，conf 0.98，**零网络成本** |
| 温州银行杭州大楼绿植租摆 | not_found（4 个候选全被筛掉） | **ok** — `wzbank.cn/purchase_info/view/page_id/36919`，一手性 high，**全自动，与人工找到的 URL 完全一致** |
| 安徽交控花卉绿植租赁 | not_found | **partial** — 取回官网 `ahjg.com/display.php?id=12479` 正文 2000 字，因无自域邮箱标 partial 待一键确认 |
| 南京师范大学相城实验小学 | not_found | 仍 not_found（gov 属地平台：`czju.suzhou.gov.cn` 首页没有采购栏目入口，栏目发现失败） |
| 杭州创悦盈室内绿植租摆 | not_found | 仍 not_found（招必得未被 Bing 收录，Bing/360 首屏全镜像） |

即：**4 个原本 not_found 的案例里，3 个已经解决或半解决，且全部是"方法修好就出来了"**。

### 7.5 剩下的两个失败，各自的性质不同（不是同一类问题）

- **相城实验小学（gov 属地平台）**：源头是**地方财政系统的政采平台**，站点结构各异、首页无采购入口。
  → 解法明确：**「城市 → 属地政采/公共资源交易平台」映射表**（我们只做 8 城，完全可以枚举），
  外加栏目路径探测。属**工程量问题**，不是能力问题。
- **杭州创悦盈（招必得）**：一手平台**搜索引擎不收录**。
  → 解法明确：**平台池广播探测**——把已登记的平台（含从成功案例里自动学到的）用项目核心名逐个站内检索。
  招必得的站内检索是 JS 表单（`#searkey` + `WebSearch('')`），需要补 `bridge_form_search` 适配器类型。

### 7.6 可达性分级（回答"理论上都能找到吗"）

要分开三级说，混在一起谈就是耍流氓：

| 级别 | 内容 | 理论可达性 | 实测 |
| --- | --- | --- | --- |
| **一级：公告正文** | 标题/正文/编号/联系人/资格要求/截止时间 | **≈100%**（发布公告就是为了让人看见，必须公开） | 温州银行/华能/安徽交控/招必得全部公开可取 |
| **二级：采购文件附件** | 招标文件/询比价文件/签章版公告 | **约 40~70%**，取决于平台是否要求报名 | 招必得签章版 PDF ✅、华能采购文件需登录 ❌、温州银行 4 个 docx ✅、东部机场 docx ✅（经江苏站拿到） |
| **三级：图纸/清单/答疑/控制价明细** | 投标决策的深层材料 | **低**，几乎都要供应商登录/报名 | 未尝试（也建议不尝试：涉及须登录的采购人系统） |

**这条分级正是用户自己观察到的现象的一般化**：`jiangsu.zhaobiao.cn` "有的能下载有的不能" ——
同一个站的不同条目、以及同一公告的不同入口，暴露的级别不同。这不是江苏站的特性，
**是所有平台「公告公开、附件要报名」这个机制的必然结果**。

### 7.7 下一步（按性价比排序）

1. **城市 → 属地政采/交易平台映射表**（8 城，覆盖相城实验小学这类 gov 项目）+ 栏目路径探测。
2. **平台池广播探测**：外部检索失败后，对已登记平台用核心名逐个站内探测；补 `bridge_form_search` 适配器（招必得型）。
3. **平台知识自动沉淀**：每次 `ok` 且一手性 high 时，把「采购人/域名 → 平台」写回登记表 —— **越用越准**，这是把一次性成功变成长期产能的关键。
4. **`summary_prev` 快照列**：现状是覆写正文不可回滚（相城实验小学那组已被错误追溯写过一次，只能靠重采回填）。
5. **接入定时**：挂到采集轮后的有界阶段（同 `detail_pass` 模式）。
