JSL 反爬实战总结：jiangsu 521 从「解不开」到「通了」

1. 问题背景

现象：jiangsu.zhaobiao.cn 的列表接口 /psearch/Dqsearch 返回 HTTP 521，纯 HTTP 抓不到任何数据。日志里一直是 origin_down(HTTP 521)。

本质：521 不是「服务器挂了」，而是 JSL（加速乐）反爬的第一关。这类反爬在政务/招采站点极其常见，cebpub、很多省市公共资源交易网都在用。

核心认知 一个站点「能 HTTP 还是必须浏览器」，不是看它有没有 JS，而是看它的反爬在第几层：
  • 简单混淆挑战（一段可逆算的 JS）→ 纯 HTTP + 自写求解器可过；
  • 重度混淆 + 浏览器指纹校验 → 纯 HTTP 无解，必须真实浏览器。

2. JSL 反爬机制全解（两阶段）

2.1 JSL 的工作原理

  1. 第一次请求 → 服务器返回 521 + 一段混淆 JS + Set-Cookie；
  2. 浏览器执行 JS，算出 __jsl_clearance_s cookie，然后 location.href 自动刷新；
  3. 服务器校验 cookie → 通过就放行内容，不通过继续 521。

2.2 阶段一：简单「字符拼接」挑战（HTTP 可解）

第一阶段 521 页面的 JS 长这样（这是抓到的真实样本）：

document.cookie = ('_')+('_')+('j')+('s')+('l')+('_')+('c')+('l')+('e')+('a')+('r')+('a')+('n')+('c')+('e')+('_')+('s')+('=')
  + (-~[]+'') + (2+5+'') + (1+7+'') + (6+'') + ... // 混淆算术
;location.href = location.pathname + location.search

它用 JS 的隐式类型转换把一堆混淆表达式拼成 cookie 字符串，例如：

混淆写法JS 真值说明
-~[]1~[] = -1，取负 = 1
~~{}0对象转数字为 NaN，两次取反变 0
1+[0]"10"数组转字符串后拼接
[2]*36数组先转 "2" 再乘
1+[2]>>23"12" 右移 2 位（注意优先级！见 3.1）

2.3 阶段二：重度混淆挑战（必须真浏览器）

通过阶段一后，服务器返回第二段更狠的混淆 JS：

<script>var _0xe5ed=['wp3Cu8K/Nw==','wqsww6fDmg==','ZyfCgsKu', ...]; // 超长 base64 数组 + 解码器

这段代码带 setTimeout 延时、多重解码，并且会检测浏览器环境（headless、webdriver 标志、指纹）。Playwright 无头浏览器在这里卡死 45 秒页面空白，而真实浏览器 6 秒自动过完。

2.4 Cookie 机制（缺一不可）

Cookie来源说明
__jsluid_s521 响应的 Set-Cookie服务器种的 uid，HttpOnly+Secure+SameSite=None
__jsl_clearance_s浏览器算出来的通行证，两个必须一起回传

__jsl_clearance_s 的值格式：<Unix时间戳>.<毫秒>|-1|<URL编码的base64(sha1)>，真实样本：

__jsl_clearance_s=1786991335.977|-1|QnM%2FuSpL2biyuTlklvFPre3gKX4%3D

3. 调试时间线与踩坑（3 个 bug）

#现象根因修复
1 解出的 cookie 值 %3D 算成 %1D，服务器不认 JS 运算符优先级错：JS 里 >> 优先级低于 +，1+[2]>>2 应算 (1+[2])>>2=3，自写求解器却先拆 +，算成 1+([2]>>2)=1 拆分顺序改为 | < ^ < <<,>> < +,- < *,/（低优先级先拆）
2 cookie 算对了还是 521 只回传了 __jsl_clearance_s，漏了 521 响应 Set-Cookie 种的 __jsluid_s 确认 CookieJar 自动收下 Set-Cookie，两个一起回传
3 两个 cookie 全对（Node 验证一致）仍然 521 服务器校验的是浏览器指纹，不只是 cookie 放弃纯 HTTP，转真实浏览器（WebBridge）
最重要的转折（认知升级） 即使用 Node.js（真 JS 引擎）验证求解结果 100% 一致、两个 cookie 全部回传，服务器依然 521。这说明 JSL 两阶段的校验对象是浏览器环境本身（TLS 指纹 / webdriver 标志 / JS 执行特征），纯 HTTP 无论 cookie 多正确都过不去。别在 HTTP 上死磕。

4. 可复用的验证技巧

  1. 用 Node.js 验证 JS 表达式：node -e "console.log(<混淆表达式>)"，和你的求解器输出逐位对比。这就是发现优先级 bug 的方法。
  2. 看 521 的 Set-Cookie 头：反爬第一步往往先种 uid cookie，必须回传。
  3. 识别多阶段：第二次 521 的 HTML 里出现 var _0x... 这种 base64 数组混淆 → 阶段二 → 直接上真浏览器，别浪费时间。
  4. 结果行结构要实地抓：jiangsu 结果行是 [类型][标题][行业][地区][日期]，日期在行内独立字段，不在标题里。靠猜标题格式会全错。
  5. 无头浏览器会被识别：Playwright headless 过不了阶段二；本机真 Chrome（WebBridge 走 Kimi 扩展的浏览器）能过。
  6. 写代码的转义坑：通过模板写代码时，s/d// 的反斜杠会被吞掉变成 s/d//，正则直接坏。写完用 repr() 验证文件真实内容。

5. 最终方案：真实浏览器（WebBridge）

jiangsu 的最终爬虫是 scripts/crawl_jiangsu_wb.py（本机运行，需 Kimi 浏览器扩展连接）：

流程：
1. webbridge navigate 到 /psearch/Dqsearch?queryword=关键词
2. 轮询等待（JSL 两阶段由真浏览器自动解 + 自动重载 + 渲染，约 6~10 秒）
3. evaluate 提取结果行：a[href 含 _v_[16位hex].html] + 行文本
4. 解析 标题/发布时间/地区（行内 [类型][标题][行业][地区][日期]）
5. 过滤：8 城 + 发布时间范围（与 HTTP 流程一致）
6. upsert 写 MySQL
成果 关键词「绿植租摆」一次抓到 40 条，日期全部为 2026-07-24 ~ 08-17；经 8 城过滤后 11 条（南京/苏州等）。NAS 上的 HTTP 定时任务把 jiangsu 标记 method=webbridge 停用，避免每轮白跑 521。

6. 通用决策树（适用于任何站点）

站点能不能爬？
├─ 纯 HTTP 直接拿到数据 ──────────────→ HTTP 爬（最快最省）
├─ HTTP 返回 521 / 403 / 验证码：
│   ├─ 521 页是「字符拼接」简单挑战 ──→ 试纯 HTTP 求解器（jsl_clearance 思路）
│   │     └─ cookie 回传仍被拒 ───────→ 浏览器指纹校验 → 真浏览器
│   ├─ 521 页是「var _0x 数组」重混淆 ──→ 阶段二 → 直接真浏览器
│   └─ 登录墙 / 付费墙 ───────────────→ 需要账号 Cookie（记录保留，等账号）
└─ 真浏览器 = 本机 WebBridge（Kimi 扩展）优先；无头 Playwright 只做渲染不碰反爬

7. 对 cebpub 的攻坚指引（下一步就用）

cebpub 现状：搜索页 JS 渲染 + DES 加密；Playwright 渲染和提取都通了（每页 15 条），但关键词 searchName 没传进请求，返回全量 72 万条。

按本文件的验证技巧，攻坚步骤：

  1. Playwright 打开 getSearch.do，page.fill("#keySearchValue", 词)；
  2. 直接 page.evaluate("getSearchParams()") 看关键词在不在返回数组里 —— 先确认填词是否生效；
  3. 监听 getStringMethod.do（加密接口）的 POST body，看 searchName= 是否带值 —— 定位关键词在哪一环丢的；
  4. 若页面 JS 读不到填的词：换 page.type 逐字输入 / 直接 $("#keySearchValue").val(词) 再触发 query()；
  5. 若加密后 searchName 依旧为空：找 query() 里关键词变量到 POST 参数的映射（页面 JS 里必然留着映射代码）；
  6. 若最终仍是「加密+指纹」双墙 → 和 jiangsu 一样，cebpub 走真实浏览器（WebBridge）让页面自己加密。
