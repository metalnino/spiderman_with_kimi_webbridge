〇、文档定位与读者

本文档是「总设计师工作区」的唯一权威产出。它不写任何能力代码，只定义标准、契约与迁移规则。

读者读什么不读什么
总设计师工作区（本区）全部。维护规范、契约、注册表——
能力工位工作区（爬虫/解析/生成/复核…）第 3、4、5 节 + 对应契约文件编排、知识库、漂移管理细节
改进层 / 运维第 5、6、7 节的观测与迁移内核实现
文档的「单一事实来源」原则 一切跨工作区的约定，只以本文档 + contracts/ + registry.json 为准。聊天记录、口头约定、记忆，一律不作数。任何约定若未落进这三个载体，视为不存在。

一、第一性原理（推导起点）

本规范的一切条款，都由以下七条原理推导而来。每条原理给出「命题 → 推导 → 本规范落点」，保证设计可追溯、可质疑。

原理 1

岗位可分解为「流程 + 记忆 + 工具」

命题：一个岗位不是原子体，而是过程（步骤与决策）、记忆（累积知识）、工具（作用于世界的能力）三者的组合。
推导：既然可分解，就能把「过程」建模为编排、把「记忆」建模为知识库、把「工具」建模为能力单元。这是「岗位 Agent 化」的合法性来源。
落点：第 2 节「员工 = 内核 + 外壳」、第 7 节「编排」、第 8 节「知识库」。
原理 2

能力单元 = 内核 + 外壳（不变量）

命题：每个员工都是「标准化能力单元」；外壳（身份/契约/配置/观测）对所有员工通用，内核（实现）因人而异。
推导：外壳统一 → 编排器可用同一套方式启动、传参、收结果、看指标、改配置；内核各异 → 每个工位独立实现，互不阻塞。
落点：第 2、3 节。这是「一套模板走所有员工」的直接来源。
原理 3

确定性优先（最小自主性）

命题：每个节点只分配「必要的最少自主性」——能规则就规则，LLM 只用于理解和生成。
推导：自主性越少 → 越可审计、越可复现、成本越低、越不易失控。投标废标代价高，可审计性优先级高于灵活性。
落点：第 4 节「自主性预算」、第 4 节的分级规则。
原理 4

契约是唯一连接（不靠记忆）

命题：多工作区彼此隔离、无共享记忆，唯一可靠的连接是机器可读、带版本号的契约。
推导：凡依赖记忆或对话的约定，会随上下文丢失而失效。因此契约必须版本化、可查询、可测试。
落点：第 5 节「契约规范」、第 6 节「漂移管理」。
原理 5

自我迭代 = 观测 + 反馈 + 改进（与内核正交）

命题：自我净化不靠「节点是不是 agent」，靠「观测 → 反馈 → 改进」的闭环。它与内核类型是正交的两个维度。
推导：一个确定性爬虫节点 + 带护栏的反馈闭环，比黑盒 agent 爬虫更可控地进化——因为你知道它在改什么、为什么改、坏了能回滚。
落点：第 3 节「观测层 + 配置层」、第 6 节「改进闭环与护栏」。
原理 6

人在环不可省（可审计 + 可追责）

命题：标书有法律效力，废标代价高；报价、关系判断、终审签字的权威必须留在人手里。
推导：自动化的目的是「把人的低价值劳动释放出来」，不是替代判断。凡是「谁签字谁负责」的位置，编排里必须是 interrupt 节点。
落点：第 7 节「人在环节点」。
原理 7

稳定性与可变性分离（漂移最小化）

命题：把「稳定核心」（字段语义、ID 格式、状态字段）与「易变边缘」（关键词、阈值、selector、提示词）分层，让易变的东西全部沉入配置层。
推导：规范「变丰满」90% 是边缘丰满（加可选字段、加指标、加词）。若核心在 T1 就想清，漂移面积自然最小。
落点：第 3 节「配置层」、第 5 节「兼容性分级」。
七条原理的优先序 冲突时的裁决顺序：原理 6（人在环）> 原理 4（契约）> 原理 3（确定性）> 原理 7（稳定性）> 其余。例：当「给某节点加自主性」与「可审计性」冲突时，可审计性优先。

二、核心模型：员工 = 内核 + 外壳

本规范最重要的一个定义，直接消解「工作流 vs agent」的二元纠结：

员工 ≠ agent。员工 = 内核 + 外壳。 一个员工是不是 agent，只由内核决定；而「成为员工」这件事，由外壳决定。套上外壳，一段爬虫代码就是一个合格员工（工作流型员工），完全成立。
① 身份层（岗位卡） —— 名称 / 职责 / 产出 / 内核类型 / 自主性预算
② 契约层（汇报接口） —— 输入 schema → 输出 schema（机器可读）
③ 配置层（可修订 SOP） —— 可调参数：关键词 / 阈值 / selector / 提示词（版本化，可回滚）
④ 观测层（绩效考核） —— 指标钩子：覆盖率 / 成功率 / 耗时 / 置信度
内核：能力实现
你已经写好的代码 / 或 LLM 调用。只有内核因员工而异，外壳四层对所有员工通用。

四层外壳是「一套模板走所有员工」的载体；内核各自不同，但都通过同一套外壳被编排器调用、被改进层读写。这就是「先开发基础功能，再套模板」的结构依据：基础功能 = 内核，套模板 = 补四层外壳。

三、外壳四层规范

每一层都给出：字段定义 + 格式 + 必填/可选 + 职责归属。四层合起来，就是一份完整的「员工定义」。

① 身份层（岗位卡）

字段说明必填归属
id员工唯一标识（如 collector / parser / generator）是总设计师
name中文岗位名（如 招标采集员）是总设计师
responsibility一句话职责是总设计师
output一句话产出（交付什么）是总设计师
coreType内核类型：rule / llm / agentic（见第 4 节）是总设计师
autonomyBudget自主性预算（见第 4 节）是总设计师

② 契约层（汇报接口）

这是「连接不同工作区」的唯一硬件接口。只定义形状（schema），不定义实现。

字段说明必填
input输入 schema：字段名、类型、必填/可选、语义说明是
output输出 schema：结构、类型、可空性、语义说明是
契约层的铁律 ① 字段名和语义属于稳定核心，T1 一次定清，之后非破坏性变更才能加；
② 输入输出必须是结构化 JSON，禁止裸文本、禁止「输出一段话让下游自己理解」；
③ 可空字段（nullable）是漂移缓冲带——初期拿不准的信息先设成可选，避免破坏性变更。

③ 配置层（可修订 SOP）

配置层是易变边缘的容器，也是「自我迭代」的抓手（原理 7）。所有会随反馈调整的东西，一律赶进这里，不进契约核心。

字段说明必填
files[]配置文件清单：路径 + 结构说明 + 谁能改是
versioning配置本身的版本化方式（与契约版本解耦）是
rollback回滚方式（快照 / git / 双份热切换）是

例：采集员的关键词、阈值、selector 都放配置层；去重 ID 的格式放契约核心，去重 ID 的具体实现放内核。

④ 观测层（绩效考核）

观测层是「反馈闭环」的入口（原理 5）。没有它，自我迭代无从谈起。

字段说明必填
metrics[]指标清单：名称、类型、说明是
reportFormat上报格式（统一 json）是
reportPath上报落点，供改进层消费是
观测指标三原则 ① 可量化：覆盖率、成功率、耗时、置信度，禁止「感觉不错」；
② 能驱动改进：每个指标要能回答「它红了之后我改什么」；
③ 增量可加：指标是可加的非破坏性字段，后来员工可以加指标，旧员工不报也不影响。

四、内核类型与自主性预算

内核有三种类型。选择依据只有一个：「下一步做什么」该由规则定，还是该由模型临场判断？

内核类型定义何时用风险
规则型 rule控制流由代码死定，路径可预测采集、去重、资格比对、格式复核低。可审计、可复现
LLM 型 llm单次 LLM 调用，输出被 schema 约束需求解析、方案生成中。需 schema 锁死 + 人复核
Agentic 型 agentic模型在任务内自主循环（多调工具/回读/重试）文档疑点排查、生成后的自我核对高。需强护栏

自主性预算（每个员工必须声明）

自主性预算是一句显式声明，回答「这个员工最多能自己做什么、绝不能自己做什么」。它是原理 3 和原理 6 的落地。

预算档位含义示例
deterministic完全确定，无任何模型决策采集员、资格评估员
suggestive只产出建议，不产生副作用，最终人拍板生成员的报价建议区间
bounded可在约束内自主，但输出必过复核解析员的需求矩阵（过复核）
红线（不可逾越） 以下三类能力永远是 deterministic 或挂在 interrupt 节点上，任何员工不得获得自主权：
① 报价（只能建议区间）；② 关系/赢面判断；③ 终审签字 / 递交动作。
决策流程图（判定内核类型） ① 这一步下一步是否固定？→ 是 → rule；
② 是否只需一次「理解/生成」且能被 schema 锁死？→ 是 → llm；
③ 是否必须模型在任务内反复试错/回读？→ 是 → agentic（且必配护栏）。

五、契约规范

契约是跨工作区的唯一硬件接口。本节规定它的文件形态、版本语义与兼容性分级。

5.1 契约文件形态

每个员工的契约是一份带版本号的 JSON 文件，放在 contracts/<员工id>/v<版本>.json。完整结构见附录 A。

5.2 版本语义

契约版本采用 MAJOR.MINOR.PATCH，但语义和软件包略有不同——由「兼容性」驱动：

位何时 +1对旧模块的影响
PATCH改说明文字、加说明性注释，schema 不变非破坏 无影响
MINOR加可选字段、加观测指标、加配置项非破坏 旧模块继续能用，只是没用上新能力
MAJOR改字段名 / 删字段 / 可选变必填 / 改语义或 ID 格式破坏 旧模块会崩或语义错，必须回溯

5.3 兼容性分级（每次变更必标注）

非破坏性（additive） —— 加可选字段、加指标、加配置、加说明。旧模块不报错、继续用。

破坏性（breaking） —— 改名 / 删除 / 改必填性 / 改语义 / 改共享 ID 格式。旧模块会崩或错。

判定口诀：「旧模块是否还能原样跑通？」能 → 非破坏；不能 → 破坏。

5.4 稳定核心 vs 易变边缘（原理 7 的落地）

稳定核心（一次定清，很少变）易变边缘（沉入配置层，随便变）
输入/输出字段名与语义关键词、阈值、selector、提示词
去重 ID / 员工间状态字段的格式地区/预算过滤条件
知识库顶层 schema观测指标（可增量加）
契约设计的元规则 在 T1 写契约时问自己：「这个字段，3 个月后我会想改它吗？」 会 → 想办法做成可选/可配置/进配置层；不会 → 才写进稳定核心。契约核心越薄，漂移面积越小。

六、漂移管理机制

针对「T1 的模块 A 没有按 T3 的新规范迭代」这一必然问题，本规范的答案不是冻结、也不是放任，而是：版本化 + 分级 + 显式迁移。

6.1 六件套

机制作用一句话
① 契约版本化 + 模块声明版本让「谁落后了」显式化每个模块带 implements: "collector/v1.0.0"
② 兼容性分级决定要不要回溯非破坏不管，破坏才进队列
③ 适配层（Anti-Corruption Layer）内核永不改，改外面薄适配契约升级 = 换适配器，不是改内核
④ 契约测试自动报「谁坏了」规范 bump 后测试一红，精确定位
⑤ 兼容窗口 + 显式回溯任务升级变成排期工作项旧模块标记 deprecated 继续跑，进 backlog
⑥ 注册表 registry漂移可见一张表看全所有员工的版本与状态

6.3 漂移可见性：注册表

设计师维护一份 registry.json，漂移必须「看得见」：

{
  "employees": [
    { "id": "collector", "name": "招标采集员", "implements": "collector/v1.0.0",
      "workspace": "爬虫工作区", "status": "current" },
    { "id": "parser", "name": "标书解析员", "implements": "parser/v3.0.0",
      "workspace": "解析工作区", "status": "current" }
  ]
}

status 取值：current（最新）/ outdated（落后，非破坏可继续跑）/ deprecated（已过兼容窗口，待下线）。

6.4 改进闭环的四个护栏（原理 5 的约束）

护栏作用
① 目标函数改进层优化什么？覆盖率？精确率？废标拦截率？没目标就没方向
② 版本化 + 可回滚每次改关键词/规则/提示词都留档，坏了一键退回
③ 灰度 + 人审小改动自动生效，大改动（换数据源、改阈值）人批一下
④ 评估集拿历史标注数据定期回归，防「改好这个、改坏那个」

七、编排规范（员工如何协作）

编排层由总设计师维护，是「业务状态机」的机器表达。它不关心内核是 rule 还是 llm，只关心：员工间的调用协议、分支、人在环节点。

7.1 统一调用协议

每个员工被编排器调用时，遵循同一协议：传入契约 input → 得到契约 output → 附带观测报告。这让编排器无需为每个员工写胶水代码。

7.2 状态机与分支

业务链上的「决策点」映射为状态机的分支；「环节」映射为员工节点；「打回/澄清」映射为回退边。

7.3 人在环节点（interrupt）

编排器的 interrupt 能力是原理 6 的机器实现：流程暂停、等人、人输入后继续。本业务至少四个 interrupt 节点：Go/No-Go 软判断、报价、方案确认、终审签字。

八、知识库规范（共享记忆）

知识库是原理 1 里「记忆」的容器，也是「越用越值钱」的资产。

库内容共享 schema 破坏性判定
资质库营业执照、资质、人员证书（带有效期）字段名/有效期格式变化 = 破坏
业绩库历史合同、中标项目（打标）打标维度变化 = 破坏
案例/方案库可复用段落 + 图——
报价库历史报价、单位成本、毛利率成本口径变化 = 破坏
客户画像库合同、续签历史、偏好、决策人——
废标条款/评分规则库评分办法、废标条款合集——
共享 schema 是漂移重灾区 知识库顶层 schema 属于「稳定核心」。它一变，所有读写它的员工（解析、生成、评估、预警）同时受影响——因此它的变更默认按 MAJOR 处理，必须走完整变更流程 + 受影响员工全量清单。

九、员工生命周期

每个新员工的诞生，都走同一条路。这条路的顺序，就是「先开发基础功能，再套模板」的正规化表达。

1. 设计师出契约
岗位卡 + 契约 v1
→
2. 工位实现内核
写/包代码，暴露接口
→
3. 套外壳 + 契约测试
补四层 + 跑测试
→
4. 验收接入
注册进 registry
→
5. 运行观测 → 迭代
观测层上报，改进层反馈

验收标准（一个员工何时算「交付完成」）

  • 契约符合：给定契约 input，输出 100% 符合 output schema；
  • 观测上报：每次运行产出观测报告，落点可被改进层消费；
  • 声明版本：带 implements 声明，注册进 registry；
  • 配置可改：配置层文件能被改进层读写并回滚；
  • 红线不越：自主性预算内的能力不触碰红线。

给「已写好但未套模板」的爬虫（你当前的状态）

套壳适配，不是重写。 已写好的内核不用推倒重来，只做一次「包壳」：
① 把现有输出包成契约要求的 output schema（通常加一个格式转换层）；
② 暴露观测指标；③ 把关键词/selector 抽成配置层文件；④ 声明 implements 版本。
半天到一天的事，不是重写。
